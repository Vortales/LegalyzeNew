# AGENTS.md — постоянные правила и инструкции для AI-агентов

Этот файл обязателен к прочтению агентом **перед каждым ответом и каждым действием** в репозитории `LegalyzeNew`.
Здесь зафиксированы постоянные требования владельца проекта.

---

## 1. Главные правила проекта (строго обязательно)

### 1.1. Новая папка для каждой новой версии — существующие папки НЕ МЕНЯТЬ
* **Каждая новая версия создаётся в новой папке.** В существующих папках ничего не менять!
* Пример: была 19 версия (`TestLegalUniversal_v19`), следующая — 20 (`TestLegalUniversal_v20`), следующая будет 21 (`TestLegalUniversal_v21`) и так далее.
* Предыдущие папки версий остаются замороженными резервными копиями. Все новые правки, сборки и тесты ведутся строго в папке актуальной версии.

### 1.2. Самостоятельное усиление логирования (без слов и напоминаний)
* **Если невозможно точно установить причину ошибок, то ты сам, своим решением усиливаешь систему логирования всего функционала и действий, без слов и просьб пользователя, и делаешь всё, чтобы программа работала у всех пользователей.**
* Не гадать, не строить предположений без приборов, не просить пользователя «пришлите ещё лог с другими настройками».
* Если в логе не хватает данных хотя бы по одному объекту, координате, вызову или состоянию — немедленно добавить точный замер, событие и шкалу в следующей версии.

### 1.3. Текущее состояние программы
* **В данный момент программа корректно работает у автора и без нареканий** (подтверждено автором: «Все отлично работает»).
* В будущем автор будет давать логи других пользователей с описанием их ошибок (папки или zip из `%APPDATA%\Legalyze\logs\<сессия>` в `browser_logs/inbox/`).

### 1.4. Работа без прав администратора
* Приложение, сбор логов и сборка EXE обязаны работать **БЕЗ прав администратора**.
* Никаких манифестов `requireAdministrator`, никаких попыток писать в системные папки, никаких реестровых веток `HKLM` с правами записи. Программа работает у любого пользователя в непривилегированном сеансе.

## 2. Порядок действий при получении логов других пользователей

1. **Положить сессию в `browser_logs/inbox/<имя-сессии>`** (или распаковать zip).
2. **Запустить разбор:**
   ```bash
   cd TestLegalUniversal_v20
   python3 tools/analyze_browser_logs.py
   ```
3. **Изучить готовый отчёт `browser_logs/analyzed/<сессия>/ANALYSIS.md`:**
   - **Раздел 0 «Машина и проверки»**:
     - `machine.fingerprint` — Windows, номер сборки, DPI, масштаб (100 / 125 / 150 %), количество мониторов, сессия (RDP / консоль), права администратора, тема оформления.
     - Риски машины (`RISK_RULES`): 125/150 %, два монитора, разный масштаб мониторов, RDP, тёмная тема, старая сборка Windows (< 19041).
     - Таблица вердиктов `selfcheck.*`: `engine`, `native_browser`, `hotkeys`, `mic`, `layout`, `window_position`, `export`, `admin_free` («ок» / «НЕ ОК»).
   - **Разделы 1–4**: хронология окна, замеры раскладки (`iw × dpr`), устой (`settle_ms`), доказательства экспорта (чипы, хэши SHA-256 файлов на диске).
   - **Раздел 5 «Что это значит»**: сопоставление с известными дефектами (`ОШИБКИ.md`).
4. **Если причина ясна на 100%:**
   - Создать новую версию папки (`TestLegalUniversal_v21`).
   - Реализовать точечное исправление.
   - Зафиксировать в `ОШИБКИ.md`: симптом, причину, что сделано, подход «использовать» и «НЕ использовать».
   - Запустить автотесты: `python3 -m unittest tests.test_backend tests.test_browser_trace tests.test_machine_profile`.
5. **Если причину точно установить невозможно:**
   - **Немедленно применить правило 1.2:** своим решением расширить систему логирования подозрительного функционала в новой папке версии (`TestLegalUniversal_v21`), добавить недостающие замеры, шкалы или проверки `selfcheck`, чтобы в следующем логе причина читалась однозначно.

## 3. Сборка исполняемого файла (Nuitka)

* **Оптимальный вариант — `--mode=standalone` (папка `build\main.dist\`)**:
  - Запуск в 3–5 раз быстрее, чем `--onefile` (~0.5–1 с против 2–5 с, нет распаковки в `%TEMP%`).
  - Меньше ложных срабатываний антивирусов.
  - Высокая стабильность.
  - Запускать через `build_standalone.bat` (подробное описание каждого ключа — `BUILD_NUITKA.md`).
* **Альтернативный вариант — `--onefile` (`build_onefile.bat`)**:
  - Использовать только если заказчику строго необходим один-единственный `.exe` файл без папки.
* При раздаче standalone-версии пользователю передаётся **вся папка `build\main.dist` целиком** (или архив этой папки).

## 4. Журнал ошибок `ОШИБКИ.md`

* Любой найденный дефект, его воспроизведение, устранение и проверка обязательно документируются в `ОШИБКИ.md`.
* Каждый дефект сопровождается чёткими маркерами:
  - **ИСПОЛЬЗОВАТЬ:** проверенный рабочий подход.
  - **НЕ использовать:** не сработавший подход с объяснением, почему он не работает (чтобы исключить повторные ошибки).
* Статусы: `ОТКРЫТА` → `СОБИРАЕМ ДАННЫЕ` → `ИСПРАВЛЕНА (ожидает проверки)` → `ЗАКРЫТА (проверено пользователем)`.
