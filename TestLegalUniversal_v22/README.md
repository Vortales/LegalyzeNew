## 0.0.0. Что нового в v18 (четыре дефекта пользователей)

### 0.0.0.1. «В Windows не установлен распознаватель речи»: можно ли поставить распознавание всем, как зависимость?

**Короткий ответ: да, но ставить нужно не речевой пакет Windows, а браузер.**

Разбор. Сообщение выдаёт не страница и не Chrome — его текст живёт в
`main.py` (`_on_speech_error`) и появляется только тогда, когда запись идёт
через **Windows System.Speech** (`speech_backend.py`). А этот путь включается
только в одном случае: **не нашлось настоящего (брендированного) браузера**, и
приложение ушло в резервный встроенный QtWebEngine. То есть сообщение — не
причина, а симптом: «браузера со штатным микрофоном нет».

Варианты «поставить распознавание как зависимость»:

| Вариант | Что даёт | Почему выбран / не выбран |
|---|---|---|
| **`Add-WindowsCapability -Online -Name "Language.Speech~~~ru-RU~0.0.1.0"`** (речевой пакет) | заставил бы работать резервный путь Windows | **отвергнут**: требует прав администратора (прямое нарушение условия «без админского режима»), ставится минутами, ломается при развёртывании без интернета и всё равно оставляет пользователя на резервном движке без штатного микрофона |
| **Поставить настоящий Chrome рядом с программой** | в нём работает **ШТАТНЫЙ микрофон самой страницы** (Web Speech + облачный сервис Google) — тот самый, который вы и требовали | **выбран**: без прав администратора, без речевых пакетов Windows, один и тот же движок у всех пользователей |
| Оставить как есть и только переписать текст ошибки | ничего | пользователь всё равно остаётся без голосового ввода |

**Что сделано.**

1. **Новый модуль `browser_fetch.py`** (только стандартная библиотека:
   `urllib` + `zipfile`, никаких новых зависимостей и ничего для сборки).
   Он читает официальный индекс
   `https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions-with-downloads.json`,
   берёт **Stable / win64**, качает архив кусками по 256 КБ с прогрессом и
   отменой и распаковывает его так, чтобы получился
   `<папка программы>\browser\chrome.exe` — ровно то, что
   `native_browser.discover_browsers` ищет **первым** (ранг 1).
2. **Предложение при старте** (`_offer_browser_install` в `main.py`): если
   настоящего Chrome нет — один раз задаётся вопрос с понятным текстом.
   * Chrome уже есть → **вопроса нет вообще** (поведение v17 не изменено);
   * отказались → ответ запоминается в `config.json`
     (`browser_install_declined`) и больше не спрашиваем;
   * отменили загрузку → тихо, без окна об ошибке;
   * нет интернета → понятное сообщение, плюс старый
     `tools\fetch_chrome.bat` для офлайн-установки.
3. **Лечение причины в момент отказа**: если микрофон всё-таки упёрся в
   отсутствие распознавателя, установка предлагается сразу там же — не нужно
   перезапускать программу руками. После установки приложение
   перезапускается само (`restart_app`) и микрофон становится штатным.
4. **Больше настоящих браузеров находится само**: добавлены каналы
   **Chrome Beta / Dev / Canary (SxS)**, **Яндекс.Браузер** и **Opera**. Это
   брендированные сборки, в которых речевой сервис есть, — раньше они
   игнорировались, и пользователь с одним лишь Яндекс.Браузером уходил в
   резервный движок.

Что осталось прежним: резервный встроенный движок никуда не делся — без
интернета и без Chrome программа всё равно запускается и работает, просто
голосовой ввод идёт через Windows и говорит об этом честным статусом.

### 0.0.0.2. Чёрный прямоугольник после «свернуть → показать»

**Симптом.** Свернули окно горячей клавишей (F2), развернули — вместо чата
чёрная область. Помогает только перезапуск или повторный выбор промта
(который заново показывает страницу), после следующего сворачивания всё
повторяется.

**Причина.** Окно браузера — дочернее (`SetParent`). Пока родитель скрыт,
скрыто и оно; Chromium к тому же приостанавливает отрисовку скрытого окна.
После `show()` сам родитель появляется, а дочернее окно либо остаётся скрытым,
либо появляется **без перерисовки**: старый кадр потерян, нового нет — вот и
чёрный прямоугольник. Повторный выбор промта «лечил» потому, что он заново
поднимал страницу и заставлял браузер отрисовать кадр.

**Исправление** (`_revive_browser`, каденс `REVIVE_STEPS` — v18.1:
0 / 120 / 300 / 600 / 1200 мс, остановка после двух совпавших измерений):

| Слой | Что делается |
|---|---|
| Win32 | `sync_now()` — **синхронный** перенос окна на место (v18.1), `ShowWindow(hwnd, SW_SHOWNA)` — показать без активации, `InvalidateRect` + `UpdateWindow` — заказать перерисовку |
| CDP | `Page.bringToFront`, событие `resize` на `window`, язык и тема |
| Раскладка | `_zoom_guard_once()`: измерение `zoom_ok()` и, если не сошлось, **немедленный** возврат зума 67 % — v18.1, раньше это делал только сторож раз в 5 с |
| Метрики | «дёрганье» на 1 px с возвратом: `apply_viewport_raw(w+1)` → 60 мс → `apply_viewport_raw(w)`. **Только если метрики уже переопределены ровно в цель зума** — проверяется измерением `innerWidth`, а не предположением. Иначе раскладка не трогается вообще |

Точки вызова: `showEvent` (но только если окно действительно было скрыто —
при первом показе лишней работы нет), `hideEvent` (ставит признак и сам
ставит браузер на место, пока окно не видно), `changeEvent` на
`WindowStateChange` (выход из «свёрнутого» состояния).
Отключается одной константой `REVIVE_AFTER_SHOW = False`.

### 0.0.0.3. Русский язык речевого ввода — приоритетно

**Симптом.** У пользователя с англоязычной Windows голос распознавался
по-английски, хотя приложение русское.

**Причина (в коде).** В `web_compat.py` язык брался так:

```js
rec.lang = documentElement.lang || navigator.language || 'ru-RU';
```

`documentElement.lang` на странице пуст, поэтому работал `navigator.language`
— а это язык **системы** (`en-US`).

**Исправление — пять слоёв, русский везде приоритетен:**

1. `window.__legalyzeSpeechLang = 'ru-RU'` — метка приложения; именно она
   стоит **первой** в выборе языка (выше `navigator.language`);
2. новый скрипт `JS_SPEECH_LANG` (`speech_lang_js()`) оборачивает
   **конструктор** `SpeechRecognition`: настоящий объект не подменяется
   (иначе облачный распознаватель Google перестал бы работать), но `lang`
   уходит прямо в настоящий IDL-сеттер движка, а любая попытка страницы его
   сменить приводит к тому же `ru-RU`. Читается тоже `ru-RU` — расхождения
   «интерфейс по-русски, распознавание по-английски» исключено;
3. ключ запуска `--lang=ru-RU`;
4. в профиль браузера пишутся `intl.accept_languages` и
   `intl.selected_languages` (`native_browser.write_locale`) — по ним сервис
   выбирает язык интерфейса и распознавания;
5. по CDP: `Emulation.setLocaleOverride` (язык страницы) и
   `documentElement.lang`.

Ключ запуска собран так, чтобы **не потерять** остальные отключаемые
возможности: `--disable-features` в командной строке ровно один, новые
значения добавляются в тот же список (проверено тестом).

### 0.0.0.4. Одинаковая светлая тема страницы

**Симптом.** У одного пользователя чат белый, у другого тёмный.

**Причина.** Chrome следует системной теме Windows (`prefers-color-scheme`) и,
кроме того, сам перекрашивает содержимое («Auto Dark Mode»,
`chrome://flags#enable-force-dark`). На машине разработчика Windows светлая —
поэтому расхождение и не проявлялось.

**Исправление — три уровня, каждый идемпотентен, любая ошибка только пишется
в лог:**

| Уровень | Что делается |
|---|---|
| Ключи запуска | `--disable-features=…,WebContentsForceDark,DarkMode` (авто-тёмная тема содержимого выключена) |
| CDP | `Emulation.setAutoDarkModeOverride{enabled:false}` и `Emulation.setEmulatedMedia` с `prefers-color-scheme: light` |
| CSS | `JS_LIGHT_THEME`: `color-scheme: light` на `documentElement`, `<meta name="color-scheme">` и стиль `:root` |

Язык и тема additionally **переприменяются сторожем зума** (раз в 5 с): после
перезагрузки страницы Chrome возвращает системные значения, и без этого слой
был бы потерян.

### 0.0.0.5. Что намеренно НЕ изменилось

* Авторизация, серверное взаимодействие, GUI, экспорт, геометрия, хоткеи,
  хранилище — как в v17.
* Зум 67 %, сдвиг окна `[-10, -20]`, шторка, скрытие кнопок в панели задач,
  сторож зума — без изменений.
* Резервный встроенный движок и мост System.Speech остались на месте как
  запасной путь: они **не** стали механизмом микрофона (это прямой запрет

* Команда сборки onefile — дословно эталонная, ни одного нового ключа:
  модуль `browser_fetch.py` подхватывается Nuitka автоматически по
  `import browser_fetch` (стандартная библиотека, зависимостей нет).

## 0.0.0-bis. Что нового в v18.1 (по приёмке v18)

Две правки по результатам приёмки: «всё работает без нареканий», кроме двух
вещей.

### 0.0.0-bis.1. Сдвиг окна браузера по Y: −20 DIP

```python
BROWSER_DY = -20     # было -40
```

Калибровка пользователя. Значение живёт в том же блоке настроек и, как прежде,
пересчитывается в физические пиксели текущего монитора: при 100 %
`inset = (-10, -20, 10, 20)`, при 125 % — `(-12, -25, 12, 25)`, при 150 % —
`(-15, -30, 15, 30)`. Подправить можно и без пересборки: `browser_dy` в
`config.json`.

### 0.0.0-bis.2. «Объекты съехали и встали на место только через пару секунд»

**Симптом.** Скрыли окно горячей клавишей, вернули — содержимое браузера
видно съехавшим (вправо-вниз или влево-вверх) и лишь через ~2 секунды
возвращается на место. Так быть не должно.

**Причины — две, обе устранены.**

1. **Асинхронный перенос окна.** `win32_embed.sync()` вызывал `SetWindowPos` с
   `SWP_ASYNCWINDOWPOS`: система лишь **отправляет** запрос в поток Chrome и не
   ждёт его. Пока скрытое окно приложения показывается, окно браузера ещё
   находится на старом месте и успевает нарисоваться — отсюда съехавшая
   картинка.
2. **Поздняя починка раскладки.** Раскладку (нативный зум 67 %) проверял и
   возвращал сторож `_ensure_zoom` — **раз в 5 секунд**. Ожидание следующего
   тика и есть те самые «пару секунд»: всё исправлялось, но с большой
   задержкой.

**Исправление.**

| Что сделано | Как |
|---|---|
| Синхронный перенос | новая `win32_embed.sync_now()` — тот же `SetWindowPos`, но **без** `SWP_ASYNCWINDOWPOS`: вызов возвращается только когда перемещение применено, поэтому съехавший кадр не успевает попасть на экран. Общий `sync()` по-прежнему асинхронный — GUI не ждёт поток Chrome на каждой смене монитора |
| Проверка сразу, а не через 5 с | проход сторожа выделен в `_zoom_guard_once()`: его вызывают и таймер, и «оживление» окна. Если измерение `zoom_ok()` не сошлось — зум возвращается **немедленно**, с пометкой `reason=revive` |
| Каденс | `REVIVE_STEPS = (0, 120, 300, 600, 1200)` мс: Chromium применяет перенос и отрисовку не мгновенно. Остановка — как только **два измерения подряд** сошлись (`_revive_settled`), дальше окно не дёргаем |
| Пока окно скрыто | в `hideEvent` браузер тоже ставится на место синхронно: он всё равно не виден, зато к следующему показу уже стоит там, где нужно |
| Без гонок | `_zoom_lock`: два потока не шлют `Emulation.setDeviceMetricsOverride` наперебой — второй проход пропускается, если первый ещё идёт |
| Измерение в логе | каждое «оживление» пишет `browser.revive step=… ok=… settled=… inset=[…] client=[…]`, а починка раскладки — `browser.zoom_restored reason=revive` |

В фоновый поток уходят только HWND и числа: всё, что зависит от Qt
(`_browser_inset()`, `placeholder.winId()`), по-прежнему выполняется в главном.

Браузер при этом **не перезапускается** — `apply_zoom` работает только через
CDP, как и раньше (проверяется отдельным автотестом).

## 0.0.0-ter. Что нового в v18.2: шторка до полной стабилизации

**Симптом, который остался после v18.1.** Чат с окном запроса съезжает
вправо-вниз, возвращается, **снова** съезжает, возвращается — и только потом
встаёт на место. То есть это не «медленно починилось», а **качка**: два
исправления подряд, а между ними — новое возмущение.

**Что происходит на самом деле.** Пока скрытое окно показывается, Chromium не
мгновенно применяет перенос окна и перерисовку, а **размер окна браузера
успевает измениться**. На нативном зуме (он берётся из настроек профиля)
ширина раскладки равна `ширина окна / 0.667`, то есть **следует за размером
окна**. Поэтому каждое изменение размера — это перевёрстка страницы прямо на
глазах: содержимое «едет» вправо-вниз и обратно. Ускорять починку тут
бесполезно: пока окно не устоялось, раскладка будет ёрзать.

**Поэтому сделано и то, и другое: устранена сама качка И введена шторка до
полной готовности** (второй вариант из вашей формулировки — «введи GUI до
полной корректной загрузки окна браузера»).

### 0.0.0-ter.1. Шторка стоит, пока браузер не устоялся

| Шаг | Что происходит |
|---|---|
| Скрытие / минимизация | шторка поднимается **заранее**, когда окно ещё не видно (`hideEvent`, `WindowStateChange` → `isMinimized`). Когда окно покажут, пользователь видит панель приложения, а не прыгающую страницу |
| Показ / разворот | `_schedule_revive()` поднимает шторку, сбрасывает счётчики и запускает каденс `REVIVE_STEPS = (0, 120, 300, 600, 1200, 2000)` мс |
| Каждый шаг | окно переносится синхронно (`sync_now`), раскладка измеряется, при необходимости прибивается, снимается «подпись» состояния |
| Критерий готовности | `REVIVE_SETTLE_N = 3` **одинаковых** измерения подряд: `innerWidth` + `dpr` + размер окна + сдвиг. Пока хоть что-то меняется — счёт сбрасывается |
| Снятие шторки | только по сигналу `revive_settled` (он уходит в главный поток Qt: измерение идёт в фоновом, а шторку снимает главный) |
| Жёсткий предел | последний шаг (2000 мс) снимает шторку в любом случае, плюс сторож на 3500 мс. **Шторка никогда не остаётся навсегда** (требование всех прежних версий) |

Во время стабилизации шторку не снимает никто: в `_hide_overlay()` и
`_hold_cover_if_needed()` добавлена проверка `_settling`. Если «оживлять»
нечего (резервный движок, страница ещё не готова) — шторка не поднимается
вообще, чтобы не залипнуть.

На устоявшейся машине (окно и раскладка не меняются) шторка снимается уже на
шаге 300 мс — то есть задержка заметна не больше, чем обычная отрисовка.

### 0.0.0-ter.2. Устранена сама «качка»

| Причина качки | Что сделано |
|---|---|
| Раскладка зависит от размера окна | при расхождении она прибивается **ОДНИМ** вызовом `Emulation.setDeviceMetricsOverride` (`apply_viewport` с `dsf = физическая_ширина / css`) — после этого ширина страницы уже не зависит от окна, и ёрзать она перестаёт. Лестница переборов `apply_zoom` (три варианта с паузами — это и были видимые промежуточные состояния) осталась только на крайний случай |
| Пропущенный проход засчитывался как успешный | раньше при занятой блокировке `_zoom_guard_once` возвращал `True`, и «всё верно» считалось без проверки. Теперь возвращается `None`, и такой проход не считается |
| Счётчик шагов не сбрасывался | `REVIVE_STEPS` начинается заново при каждом показе окна |

### 0.0.0-ter.3. Что видно в логе

```
browser.revive step=0 ok=False settled=0 signature=[658, 1.0, 439, 728, (-10, -20, 10, 20)]
browser.zoom_pinned reason=revive         ← раскладка прибита одним вызовом
browser.revive step=1 ok=True settled=1 …
browser.revive step=2 ok=True settled=3 …
browser.revealed stable=True              ← шторка снята, браузер на месте
```

Если `browser.revealed stable=False` — браузер не устоялся за 2 с (окно всё
ещё «плавает»): пришлите лог, по полю `signature` видно, что именно меняется.

## 0.0.0-quater. Что нового в v18.3: GUI прогрузки наивысшим приоритетом, окно трогаем один раз

Приёмка v18.2: **«мигает очень сильно и только спустя 2 секунды всё
становится нормальным»**. Две причины, обе устранены.

### 0.0.0-quater.1. Мигание рождала сама стабилизация

В v18.2 каждый шаг каденса **дёргал окно браузера**: `SetWindowPos` +
`ShowWindow` + `InvalidateRect` + `Page.bringToFront` + «дёрганье» метрик
на 1 px — восемь раз за две секунды. Каждое такое действие заставляет
Chromium пересобирать кадр, а **Chrome при этом поднимает своё окно** — ровно
поэтому он и возвращает кнопку в панели задач не сразу. Окно браузера
оказывалось поверх шторки на кадр-другой: вот это и было «сильное мигание».

**Теперь, пока GUI прогрузки стоит, окно браузера не трогается вообще.**
Шаги каденса только **измеряют** (`innerWidth`, `dpr`, размер окна, сдвиг).
Вся работа с окном переносится в `_finalize_and_reveal()` и выполняется
**один раз**, когда измерения показали, что браузер устоялся:

```
sync_now()  →  ShowWindow(SW_SHOWNA)  →  InvalidateRect/UpdateWindow
   →  Page.bringToFront  →  раскладка: измерение и, если нужно, прибивка
   →  «дёрганье» метрик  →  пауза 180 мс (кадр должен лечь)  →  снять GUI
```

### 0.0.0-quater.2. GUI прогрузки — тот же, что на «Ожидании страницы», и не снимается раньше времени

Раньше при развороте поднималась только шторка (панель цвета фона). Теперь
поднимается **ровно тот же индикатор, что на этапе «Ожидание страницы»** —
`LoadingOverlay`, отдельное окно с `WindowStaysOnTopHint` и `force_topmost`,
то есть наивысший приоритет над окном браузера — плюс шторка под ним. Пока
стабилизация идёт, индикатор каждые 120 мс возвращается наверх
(`_hold_cover_if_needed`), чтобы Chrome не перекрыл его своим окном.

**Раньше 1,2 с GUI не снимается при любых измерениях.** В v18.2 три
одинаковых измерения набирались уже к 300-й миллисекунде — но возмущение у
Chromium начинается **позже** (по вашей приёмке — около двух секунд), поэтому
«совпало три раза» на ранних кадрах ни о чём не говорило: GUI снимали, а
браузер потом всё равно ёрзал. Теперь:

```python
REVIVE_STEPS   = (0, 150, 350, 600, 900, 1300, 1800, 2400)  # мс
REVIVE_SETTLE_N = 3       # одинаковых измерения подряд
REVIVE_MIN_MS   = 1600    # раньше этого срока GUI не снимаем
REVIVE_FINAL_MS = 180     # пауза после финальной правки
```

Снимаем GUI, только когда **и** прошло `REVIVE_MIN_MS`, **и** последние
`REVIVE_SETTLE_N` измерения одинаковы. Либо на последнем шаге (2400 мс) —
жёсткий предел, плюс сторож на 4900 мс.

### 0.0.0-quater.3. Что видно в логе

```
browser.revive step=0  ms=0    settled=1 signature=[658, 1.0, 439, 728, (-10, -20, 10, 20)]
browser.revive step=1  ms=150  settled=2 …
browser.revive step=5  ms=1300 settled=6 …
browser.revealed stable=True     ← окно поставлено один раз, GUI снят
```

Обращений к окну браузера за весь разворот — **три** (`sync_now`,
`show_window`, `invalidate`) вместо десятков.

## 0.0.0-quinquies. Что нового в v19 (разбор «Error - 1»)

Папка `Error - 1` — это два лога одного пользователя: `diagnostic.jsonl`
(1926 записей, сессия 84 с) и `stacks.log`. Ниже — что в них написано на самом
деле, что из этого исправлено и как это теперь видно в логе.

### 0.0.0-quinquies.1. Настоящий краш: access violation в `ITaskbarList`

```
Current thread 0x00002bc8 (most recent call first):
  File "...\win32_embed.py", line 603 in _com_call
  File "...\win32_embed.py", line 634 in taskbar_delete_tab
  File "...\win32_embed.py", line 671 in hide_from_taskbar
  File "...\main.py", line 2616 in hide_taskbar
```

Кнопку браузера в панели задач убирал вызов слота vtable COM-объекта. Сам
вывод слота делался **средствами Python**:

```python
table   = ctypes.cast(ctypes.c_void_p(int(interface)), ctypes.POINTER(ctypes.c_void_p))
address = int(table[slot] or 0)     # ← разыменование чужой памяти
```

Вызов через ctypes защищён (AV превращается в `OSError` — поэтому в одном логе
пользователя «всего лишь» исключение), а чтение `table[slot]` — **нет**: это
обычное чтение по указателю, и при плохом адресе процесс умирает целиком, без
возможности перехвата. Именно это и произошло во втором прогоне.

В том же логе видна и причина: `win32.com_empty_slot slot=3` — слот `HrInit` в
vtable пустой, то есть указатель получен не на тот объект. Приложение это
увидело, но всё равно пошло вызывать соседний слот и записало
`win32.taskbar_deleted` — **успех, которого не было**.

**Что сделано:**

1. Память читается через `ReadProcessMemory` на собственный процесс: плохой
   адрес даёт «не прочиталось», а не смерть процесса
   (`win32_embed.read_pointer`).
2. Объект проверяется **до** любого вызова: читаются все 8 слотов `ITaskbarList`,
   ни один не должен быть пустым и слоты не должны повторяться
   (`win32_embed.com_vtable`). Не прочиталось — COM отключается,
   в логе `win32.com_abort` с причиной.
3. Успех — это факт: `win32.taskbar_deleted` пишется только с настоящим
   `HRESULT` (`hr >= 0`), иначе `win32.taskbar_failed`, а функция возвращает
   `False`. Ложных успехов больше нет.

### 0.0.0-quinquies.2. «Браузер не прогрузился»: ворота готовности

Из лога пользователя:

```
browser.target_chosen  pages=["https://www.google.com/search?udm=50&aep=11"]
page.probe  category=google ready=interactive bodyChildren=47 fileInputs=0 editors=2
webengine.chat_ready                       ← через 1,06 с после запуска
main.snapshot  overlay_visible=false       ← GUI загрузчик снят
```

Старый признак готовности (`READY_SCRIPT`) — «на странице есть видимое текстовое
поле». Он срабатывает уже на `readyState == "interactive"`, то есть **пока
страница ещё грузится**. Поэтому индикатор исчезал через секунду, а пользователь
видел недогруженную тёмную страницу: объектов на ней ещё не было, а приложение
уже считало чат готовым.

**Что сделано.** Готовность — это теперь ворота (`wait_for_chat_surface`), и они
требуют всё вместе:

* `document.readyState == "complete"` — догрузилось, а не «почти»;
* есть поле ввода (во что писать запрос);
* **два одинаковых замера подряд** — страница устоялась, а не совпала случайно;
* тема приведена к светлой, если замер показал тёмную (§0.0.0-quinquies.3).

Каждый замер пишет `page.surface`: какая это поверхность (`verdict`), её
готовность, есть ли поле ввода, поля для файлов и прикреплённые файлы, вошёл ли
пользователь в аккаунт, сколько ресурсов запрошено. Одинаковые замеры подряд
склеиваются, поэтому лог не зарастает. Итог виден в `webengine.chat_ready`
(`ready`, `verdict`, `blocked`, `rounds`, `theme_repairs`).

Если чата здесь не будет никогда (`verdict` = `login` / `consent` /
`browser_error`), ждать бессмысленно: ворота возвращают `blocked`, в логе
появляется `warn.surface_blocked`, а приложение **не падает** — страница
показывается, чтобы пользователь мог войти в аккаунт, а в строке состояния
написано что делать.

### 0.0.0-quinquies.3. Тёмная страница: замер вместо надежды

Жалоба: «он у него нестандартно темного цвета». В логе при этом —

```
page.language_theme  locale=ru-RU auto_dark=false color_scheme=light
```

Приложение **применило** светлую тему, но ни разу её не **проверило**. Теперь
цвет страницы замеряется (`page.theme_probe`: цвет `body`, `color-scheme`,
`prefers-color-scheme`), и если замер тёмный — светлая тема применяется заново
(не чаще `THEME_MAX_REPAIRS` раз), а в логе остаётся и цвет, и факт починки
(`warn.dark_theme_measured`). Тёмный фон определяется по яркости, а не по
системному свойству: сервис может красить страницу своей разметкой.

### 0.0.0-quinquies.4. Экспорт: причина вместо 92 молчаливых попыток

Из лога: 92 × `upload.attempt injected=true`, при этом `upload.state
present=0`, `page.probe fileInputs=0`, `attempts_failed=0`. То есть поток 84
секунды впрыскивал файлы в страницу, где **некуда прикреплять**, и не считал это
ошибкой — по логу всё выглядело успешным.

**Что сделано:**

* каждая попытка пишется целиком: `kind`, `injected`, `bytes`, `ms`, имя файла,
  счётчик пустых проверок;
* пустые проверки считаются; как только их становится больше
  `UPLOAD_BLOCK_THRESHOLD`, в лог уходит `warn.upload_blocked` **с вердиктом
  поверхности** и числами (`files`, `chips`, `composer`, `account`, `pending`);
* приложение само исправляет поверхность: если на странице нет прикрепления,
  один раз открывается `SURFACE_FALLBACK_URL` (`https://gemini.google.com/app`)
  — чат, под который и написана автоматизация. Событие
  `page.surface_corrected`, автоматизация перезапускается, ворота проходятся
  заново. Повторно это не сработает никогда (`_surface_corrected`).

На машине, где экспорт работает, ни одна из этих веток не выполняется.

### 0.0.0-quinquies.5. Предсказуемость «как в Docker»

«Один и тот же exe ведёт себя по-разному на двух Windows 10» — это всегда
разница окружения, а не кода. Раньше его состояние в логе отсутствовало вообще.
Теперь перед запуском браузера пишется **`env.contract`**: путь, размер и время
изменения браузера, его вид, порт, профиль, URL, размер окна, язык, тема, зум
(`ZOOM` и `ZOOM_LEVEL`), **полный список ключей запуска** и отключённые
возможности. Два таких события от разных пользователей сравниваются построчно:
разошлось — значит дело в окружении.

Профиль браузера приводится к эталону и **проверяется чтением**: зум,
`Accept-Language` и право микрофона читаются обратно из `Preferences`
(`browser.prefs_verified`), а расхождение пишется как `browser.prefs_drift` с
перечнем (`zoom`, `locale`, `mic`). Записанное больше не считается применённым.

### 0.0.0-quinquies.6. Что именно добавлено в логирование

| Слой | Что пишется |
|---|---|
| Запись | **асинхронно**, отдельным потоком: поток GUI никогда не ждёт диск. Потеря записи при переполнении тоже видна (`dropped_records` в сводке) |
| Формат | `diagnostic.jsonl` (машине) + **`events.log`** (человеку, те же события строкой) + **`summary.json`** (итог сессии) |

### 0.0.0-quinquies.8. Разворот окна (F2): GUI снимается по замеру страницы

Жалоба: «во время использования хоткея „Окно“ и возвращения его из скрытого
состояния в видимое объекты внутри браузера не перемещаются сразу на заданное

* минимум поднят: `REVIVE_MIN_MS` **1600 мс** (было 1200 — на части машин

* перед снятием ждём `document.readyState == "complete"`, но не дольше

Окно браузера при этом, как и в v18.3, трогается **один раз** — вся работа с
ним делается в финализации, поэтому Chromium не перерисовывается на глазах у
пользователя и не поднимает своё окно поверх шторки.

## 0.0.0b. Что нового в v17 (две правки)

### 0.0.0.1. Ни одного промелькнувшего элемента на этапе «Ожидание страницы»

**Симптом.** Пока идёт «Ожидание страницы ИИ…», в GUI на мгновение появлялся
браузер с неудалёнными элементами.

**Причина (найдена в коде).** Окно браузера и шторка `browser_cover` — оба
настоящие HWND-окна внутри плейсхолдера. `SetParent` ставит НОВОЕ дочернее
окно **поверх всех соседей**, и в `win32_embed.embed()` порядок был такой:

```python
user32.ShowWindow(hwnd, SW_SHOW)   # окно браузера показали первым
sync(user32, hwnd, parent, inset)  # и только потом поставили на место
```

То есть окно браузера показывалось, когда шторка была ПОД ним. Второй слой
причины: сторож шторки в v16 требовал `self.native_mode`, а он включается
только в `_on_browser_ready` — значит весь этап «Ожидание страницы» (старт
процесса, поиск окна, встраивание) шторку вообще никто не держал.

**Исправление.**

| Что сделано | Как |
|---|---|
| Порядок в `embed()` | сначала `sync()` (окно ставится на место), затем **подъём шторки**, затем `ShowWindow`, затем подъём шторки снова. Окно браузера ни на мгновение не оказывается выше шторки |
| Принудительный подъём | новая `win32_embed.raise_window()`: `SetWindowPos(hwnd, HWND_TOP, 0,0,0,0, NOMOVE\|NOSIZE\|NOACTIVATE)`. Одного `QWidget.raise_()` мало — нужен Win32 z-порядок |
| Сторож работает с самого старта | в `_poll_browser_focus` убрано условие `native_mode`: шторка держится с момента `_start_chrome`, а не только после `ready` |
| Повторный подъём | `_on_browser_ready` поднимает шторку сразу и затем на 300/800/1500/2500/4000 мс — тем же каденсом, что и скрытие кнопки в панели задач: Chrome меняет z-порядок не сразу |
| hwnd шторки | `NativeHost.cover_widget` → `embed(..., cover=hwnd)` |

### 0.0.0.2. Окно ожидания — до момента выбора промта

**Симптом.** На чистом первом запуске окно ожидания (GUI поверх браузера)
появлялось на секунду и пропадало, хотя должно стоять, пока промт не выбран.

**Причина.** `_on_hwnd()` планировал `_reveal_page()` через 250 мс, а тот
безусловно снимал и окно ожидания, и шторку:

```python
def _reveal_page(self):
    self._hide_overlay()          # ← снимает ВСЁ, независимо от промта
```

Дальше `_load_prompt()` показывал шторку «Выберите промт» и открывал диалог,
а диалог её скрывал — в итоге окно ожидания мелькало и пропадало, а браузер
оказался приоткрыт.

**Исправление.** Одно условие в одной точке — `_hide_overlay()`:

```python
def _hide_overlay(self):
    self.overlay_state.emit("", "", False)
    if not self._prompt_selected():     # v17
        self._cover_to_top()            # браузер остаётся закрытым
        return
    self.browser_cover.hide()
```

`_prompt_selected()` читает `cfg["selected_prompt"]` (если конфиг недоступен —
возвращает `True`, чтобы никогда не заблокировать интерфейс). Отсюда:

* пока промт не выбран — браузер закрыт шторкой, окно ожидания на месте;
* выбрали промт → пошла выгрузка → `upload.attachments_confirmed` →
  `_on_files_attached` сам снимает шторку → страница открывается;
* если диалог закрыли без выбора — шторка остаётся, но **верхняя панель с
  кнопкой «Промт» не перекрыта** (окно ожидания занимает только область
  браузера), поэтому тупика нет: можно нажать «Промт» в любой момент.

Прежняя логика не изменена: при уже выбранном промте всё работает ровно как
в v16.

### 0.0.5.1. Первый запуск: экспорт больше не ждёт нажатия «Промт»

```python
sel = self.cfg.get("selected_prompt", "")
```

информационную (не красную) шторку. Выбрали промт → сохраняется
`selected_prompt` → `_reload_prompt()` → `_load_prompt(force=True)` →
экспорт. В логе появляется `prompt.picker_auto`.

**Что НЕ тронуто**: рабочая ветка (промт уже выбран) — ни одного изменения;
авторизация, серверное взаимодействие, GUI, экспорт и микрофон — как были.

## 0.0. Что изменено против v13

### 0.0.1. Сдвиг окна браузера: X −10, Y −40 DIP (подобрано, не угадано)

В v13 поле ввода промта оказалось слишком низко. Вместо правки «на глаз» в
`pre14` была собрана измерительная панель: администратор двигал окно браузера
ползунками и снимал показания. Итоговый отчёт с Windows:

```
Окно браузера (DIP): x -10..443, y -20..715  (453x735)
поле ввода: textarea  прямоугольник DIP: {'l': 64.0, 't': 615.8, 'r': 360.3, 'b': 631.8}
below_dip = -93   ниже видимой нижней кромки (норма <= 0)
left_dip  = -34   левее видимой левой кромки (норма <= 0)
right_dip = -49   правее видимой правой кромки (норма <= 0)
```

То есть достаточно сдвинуть окно браузера на **X −10, Y −40 DIP** — все
элементы встают на места. В v15 это значение вшито:

```python
BROWSER_DX = -10   # DIP
BROWSER_DY = -20   # DIP
```

**Размер окна при этом НЕ меняется** — только положение. Это принципиально:
если урезать раскладку внутри окна, поверхность перестанет равняться окну и
внизу появится незакрашенная полоса. Сдвиг такого побочного эффекта не имеет —
панели GUI (сверху 54, снизу 30, по бокам 20 DIP) и так перекрывают всё, что
окно выставило наружу.

Сдвиг переводится в физические пиксели текущего монитора, поэтому при 100 %,
125 % и 150 % он в DIP один и тот же:

| Масштаб | Сдвиг в физических px | Окно |
|---|---|---|
| 100 % | (−10, −40) | x=−10 y=−40, 453×735 |
| 125 % | (−12, −50) | x=−12 y=−50, 566×919 |
| 150 % | (−15, −60) | x=−15 y=−60, 680×1102 |

#### Почему первая v15 показывала НЕ так, как pre14

Цель раскладки считалась от **плейсхолдера** (453×735 DIP), а реальная
клиентская область **самого окна браузера** — 439×728 (это число пришло из
замера pre14). Из-за этого масштаб получался

* от плейсхолдера: `dsf = 439 / 679 = 0.6465` → страница на **3 % мельче**;
* от окна браузера: `dsf = 439 / 658 = 0.6672` → совпадает с нативным
  рендером (именно это замерил pre14: `css 658x1091`; сейчас v15 получает
  ровно те же числа).

Теперь логический размер берётся у САМОГО окна браузера
(`_browser_logical_size()` → `_zoom_size()`), и, если не задано поправок,
цель совпадает с нативным рендером: переопределять нечего вообще.

#### Что ещё было не так в первой v15 (обе ошибки закрыты)

1. **Сдвиг считался не от того размера.** `host.inset` вычислялся ДО того,
   как `self.browser_host` был назначен, поэтому `_placeholder_physical_size()`
   уходил в резерв `(413, 651)` вместо реального `(453, 735)` — и сдвиг
   получался на 9 % меньше нужного: лог показывал `inset: [-9, -18, 9, 18]`
   вместо `[-10, -20, 10, 20]`. Теперь `browser_host` назначается первым, а при
   готовности браузера сдвиг пересчитывается по настоящему плейсхолдеру.
2. **`_browser_logical_size` вызывал несуществующий `_monitor_scale`** —
   `AttributeError` в `_on_browser_ready` обрывал запуск веб-автоматизации:
   элементы браузера не скрывались и файлы не экспортировались. Метод добавлен,

### 0.0.3. «Сырой» браузер не виден никогда

Окно браузера — настоящее HWND-окно внутри плейсхолдера, а обычный виджет Qt
(**любой**, включая шторку) всегда рисуется **ПОД** ним. Поэтому шторка
`browser_cover` сделана нативным окном (`WA_NativeWindow`): только так её можно
поднять выше браузера. Плюс:

* браузер стартует за пределами экрана (`--window-position=-8192,-8192`) и
  переезжает на место только после встраивания;
* шторка показывается до старта и поднимается при каждом событии встраивания;
* поверх GUI лежит отдельное окно загрузки (`LoadingOverlay`,
  `WindowStaysOnTopHint`) — оно и закрывает всё до готовности страницы.

### 0.0.4. Никаких всплывающих консолей

## 0. Нативный зум 67 %: как это работает (v9) и что исправлено в v13

### 0.0.1. Расположение поля ввода и поля ответа ИИ (правка v13)

Плейсхолдер браузера занимает **всё окно** — `setGeometry(0, 0, 453, 735)` DIP.
А ширина раскладки считалась от воображаемого «слота» между рамками:

```python
# v9, MainWindow._placeholder_logical_size
return (int(W - 2 * self.side_inset),                 # 413 вместо 453
        int(H - self.top_inset - self.bottom_inset))  # 651 вместо 735
```

`413 / 0.667 = 620 CSS px` вместо `453 / 0.667 = 680 CSS px`. Сайт верстал
слишком узкую раскладку, поэтому поле ввода и поле ответа ИИ стояли не на
своих местах и съезжали вправо.

| Было (v9) | Стало (v13) |
|---|---|
| логический размер = «слот» 413×651 DIP | `browser_placeholder.width()/height()` — **453×735 DIP**, размер самого виджета |
| физический размер = клиентская область плейсхолдера | клиентская область **окна браузера** (`_browser_physical_size`): рамка/заголовок окна больше не срезает низ страницы вместе с полем ввода |
| высота раскладки = `логическая / 0.667` | `target_css()`: `dsf = физическая_ширина / css_ширина`, `css_высота = физическая_высота / dsf` — поверхность **точно равна** клиентской области окна |

Проверено симуляцией на модели Chrome: 100 % / 125 % / 150 % / 175 % / 200 %,
с рамкой окна и без, с применённым зумом профиля и без — во всех случаях
`innerWidth` = **680 CSS px**, зум = **0.667**, `innerWidth × dpr` **ровно
равно** физической ширине окна (раскладка вписана, а не обрезана справа).

### 0.0.2. Жёлтая полоса про неподдерживаемый флаг (правка v13)

Chrome показывает эту полосу для switch'ей из своего списка неподдерживаемых —
в отчёте назван `--use-fake-ui-for-media-stream`. Он удалён; вместе с ним
удалён и `--use-fake-device-for-media-stream=disabled` (этот switch подменяет
микрофон фейковым сигналом, он не нужен в принципе). **Остальные флаги v9 не
тронуты.**

Микрофон без флага — права пишутся в сам профиль (`native_browser.write_permissions`),
точно так, как их пишет Chrome после нажатия «Разрешить»:

```json
"profile": {"content_settings": {"exceptions": {"media_stream_mic": {
    "https://google.com:443,*": {"setting": 1, "secondary_pattern": "*", ...}}}}}
```

`setting: 1` = ALLOW; файл сливается с содержимым профиля и заменяется
атомарно, права пишутся при каждом запуске. Плюс прежний CDP-грант
(`Browser.grantPermissions` + `Browser.setPermission`), а состояние права
проверяется и попадает в лог: `browser.mic_granted state=granted`.

### 0.0.3. Чего в v13 НЕТ

Ни перезапуска браузера ради зума (`--force-device-scale-factor`), ни нажатий
клавиш, ни хуков — лестница зума работает только через CDP, поэтому она не
может оборвать сессию, поднять шторку или сломать кнопки GUI (автотест
запрещает в `apply_zoom` слова `press`, `restart`, `keybd`, `hooks`).

### 0.1. Симптом

### 0.1. Симптом

В v8 при 67 % «весь текст съехал вправо» и уходил за границы окна: чат был
виден частично, его содержимое смещено вправо, справа — пусто/обрезано.

### 0.2. Причина (подтверждена кодом v8)

v8 задавал раскладку так:

```python
# v8, native_browser.apply_viewport
page.send("Emulation.setDeviceMetricsOverride", {
    "width": 680, "height": 1102, "deviceScaleFactor": 1, "mobile": False})
```

`Emulation.setDeviceMetricsOverride` задаёт **размер раскладки в CSS-пикселях**,
но сам по себе **не масштабирует** отрисовку. Окно браузера — плейсхолдер
453x735 DIP (это всё окно приложения), а страница версталась на 680 CSS px:
она оказалась ШИРЕ окна, центр уехал вправо, текст вышел за границу.
(В v9 ширина раскладки из-за «слота» получалась 620 CSS px — то есть слишком
узкой, отсюда съехавшие вправо поле ввода и поле ответа; в v13 это исправлено,
см. §0.0.1.)

Проверка v8 (`verify_viewport`) смотрела только на `innerWidth` — формально
«680» совпадало, и дефект пропускался.

### 0.3. Исправление: нативный зум, как в работающих сборках

1. **Зум пишется в профиль ДО запуска** (`native_browser.write_zoom`):

   ```json
   "partition": {"default_zoom_level": {"x": -2.2239010857415455},
                 "per_host_zoom_levels": {"x": {"google.com": {...}}}}
   ```

   Chrome хранит зум как «уровень»: `factor = 1.2 ** level`, поэтому
   `log(2/3) / log(1.2) = -2.2239016` — ровно 67 %, то же значение, что
   использовала работающая сборка `release/`. Браузер стартует сразу с зумом:
   страница верстается в `размер окна / 0.667` CSS px и масштабируется в окно.
   Ничего не обрезается и не смещается — это то же самое, что вручную нажать
   Ctrl+«-» до 67 %.

2. **Зум ИЗМЕРЯЕТСЯ, а не предполагается** (`native_browser.zoom_ok`):

   * раскладка = `логический размер (DIP) / 0.667` CSS px — не шире, не уже;
   * `innerWidth x devicePixelRatio` = **физическая** ширина окна — то есть
     раскладка действительно вписана в окно, а не выходит за него.

   Второй пункт и есть регресс-тест на дефект v8: при CSS 680 и `dpr = 1`
   произведение даёт 680 вместо 453 — страница не вписана.

3. **Если профиль проигнорирован** (другой Chrome, чужой профиль, политики) —
   зум выставляется принудительно по CDP и **снова измеряется**: сначала
   `deviceScaleFactor = физическая / css` (эмулируемое устройство становится
   точно равным окну — сжатие без обрезки), затем то же с `fitWindow`, затем
   просто `fitWindow`. Побеждает то, что реально сработало; источник виден в
   логе (`browser.zoom source=native|emulation-dsf|emulation-dsf-fit|emulation-fit`).

4. **Сторож зума**: раз в 5 с в фоновом потоке проверяет метрики и возвращает
   зум после перезагрузки страницы или смены таргета (`browser.zoom_restored`).

Итог: раскладка **680 CSS px по ширине при 67 %** (453 DIP / 0.667) — ровно как в
работающих сборках v1–v7 и в `release/`, и **одинаково при 100 %, 125 % и 150 %**
(проверено расчётом: при 125 % физическая ширина 566 px, dsf = 566/680 = 0.833 =
1.25 x 0.667, раскладка та же; по высоте поверхность всегда равна клиентской
области окна).

## 1. Что было не так: два тупика

### 1.1. Встроенный движок (v1–v7): функционал есть, микрофона нет

QtWebEngine — это Chromium **без ключей Google**. Запись голоса на странице — не
`getUserMedia` и не «локальное распознавание», а облачный пайплайн вендора:

* объект `SpeechRecognition` в QtWebEngine есть, но `start()` **роняет
  рендер-процесс** (в `speech_recognition.cc` требуется API-ключ, которого в
  сборке нет) — это подтверждено логами v4 и исходниками Chromium;
* `getUserMedia` в этой поставке недоступен (QTBUG-55108);
* AssemblyAI прямо пишет: «Build a desktop app on Electron, and the API may be
  present and simply never return a result» — объект есть, результата нет.

Поэтому v1–v7 подменяли речь мостом на Windows `System.Speech`. Это **не
штатная запись страницы**, качество другое, поведение другое, и это ровно то,
что вы потребовали убрать. Мост оставлен в поставке только как аварийный путь
для резервного встроенного движка.

### 1.2. `release/` (внешний Chromium): микрофон есть, стабильности нет

Эталонная сборка запускала portable-`chromium` отдельным процессом, встраивала
его окно в GUI и управляла им по CDP. Микрофон там работал настоящий. Три
сообщенные вами поломки — не «мистика chromium», а конкретные дефекты, которые
читаются в коде:

**Поломка 1. «Принять все» в Испании.** Свежий профиль в ЕС получает перед
чатом страницу согласия. Кликера согласия в `release/` нет вообще, а выбор
цели CDP был таким:

```python
google_pages = [t for t in pages if urlsplit(t['url']).hostname in
                ('google.com', 'www.google.com', 'gemini.google.com',
                 'accounts.google.com', 'consent.google.com')]   # <-- consent!
chosen = google_pages[0]
```

`consent.google.com` **подходит под это условие**. Автоматизация встаивалась в
стену согласия и ждала чат, которого там нет → «браузер запускается, висит,
ничего не работает».

**Поломка 2. «Процесс висит, работает некорректно».** Причины три, и все
устранимы: (а) профиль занят старым процессом Chromium — новый запуск
мгновенно завершается, передав управление синглтону, и отладочный порт не
открывается; (б) зависание GPU/драйвера (в логе пользователя — Parsec Virtual
Display Adapter и гибридная Intel+NVIDIA); (в) окно ищется один раз и без
проверок, а при неудаче `SetParent` код откатывался в отдельное окно 900×700
в точке (80,80) — «браузер есть, но пользоваться им нельзя».

**Поломка 3. «Широкое окно и просто надпись ИИ».** Вот она, построчно:

```python
user32.GetClientRect(parent, byref(rect))      # ФИЗИЧЕСКИЕ пиксели
user32.SetWindowPos(chrome, HWND_TOP, -10*dpr, 0, p_width, p_height, ...)
```

`GetClientRect` отдаёт **физические** пиксели, а Chromium — per-monitor DPI
aware (PMv2) и читает размер окна в **DIP**. На экране 125 % окно 453×735
становится 566×919 физических пикселей; эти числа передаются Chromium, который
считает их DIP — и получает вьюпорт ~1,5× шире. Сайт переходит на десктопную
раскладку и показывает центрированную надпись «ИИ» вместо чата. У пользователя со
100 % масштабом всё выглядит нормально, у остальных — нет. Отсюда «у половины
пользователей не работает».

### 1.3. Почему «написать свой движок» не нужно и вредно

Свой движок = свой Chromium без ключей = тот же тупик 1.1, плюс год поддержки
и отсутствие WebRTC/кодеков/сети. Нужен не свой браузер, а **правильный
браузер, запущенный правильно**.

## 2. Решение (v8 + зум v9)

**Настоящий Chromium/Chrome работает отдельным процессом, его окно встроено в
GUI, им управляет CDP, а микрофон — штатный, самим браузером.**

```
┌─ Legalyze (Qt) ────────────────────────────────────┐
│  панель, баланс, хоткеи F2/F3, шторка              │
│  ┌ browser_placeholder ────────────────────────┐   │
│  │  HWND настоящего Chrome (WS_CHILD, SetParent)│   │
│  │  страница google.com/ai — как в браузере     │   │
│  └──────────────────────────────────────────────┘   │
└────────────────┬────────────────────────────────────┘
                 │ CDP (127.0.0.1, случайный порт)
        ┌────────▼─────────┐
        │ chrome.exe       │  --app=… --user-data-dir=… --use-fake-ui-for-media-stream
        │ микрофон: Web Speech │  профиль: %APPDATA%\Legalyze\browser-profile
        └──────────────────┘
```

| Модуль | Что делает |
|---|---|
| `native_browser.py` | поиск браузера, флаги запуска, выбор цели CDP, **нативный зум 67 % (запись в профиль + измерение + принудительная установка)**, выдача прав микрофону, контроль живости |
| `win32_embed.py` | поиск окна, проверяемое встраивание (`SetParent` + проверка `GetParent`), синхронизация геометрии, откат при любой ошибке |
| `browser_focus.py` | передача фокуса дочернему окну по клику (без хуков и перехвата клавиш) |
| `main.py` | `NativeHost` — супервизор запуска; `ChromeWorker` — вся CDP-автоматизация (файлы, промт, отправка) без изменений |
| `web_compat.py` | `CONSENT_CLICK_JS` — кликер согласия на всех языках Google |

| `qt_browser.py` + `speech_backend.py` | резерв: встроенный QtWebEngine с Windows-диктовкой, если браузера нет |

### 2.1. Штатный микрофон (главное)

1. Права микрофона выдаются **заранее**: CDP `Browser.grantPermissions` +
   `Browser.setPermission` (в настоящем Chrome это работает; в QtWebEngine тот
   же вызов падал с `-32000`) и флаг `--use-fake-ui-for-media-stream`. Никакой
   всплывашки «разрешить микрофон» ни у кого и никогда.
2. **Шим речи в нативном режиме НЕ устанавливается.** Подменять
   `SpeechRecognition` в настоящем Chrome нельзя — им сайт и пишет голос.
   Шим остался только для резервного встроенного движка.
3. F3 / кнопка «Микрофон» → клик по **кнопке микрофона страницы**
   (`JS_START_RECORDING`), затем **обязательная проверка** `JS_CHECK_RECORDING`:
   страница действительно перешла в режим записи. Раньше этой проверки не
   было — отсюда «нажимаю на микрофон и всё, сразу отправка без записи».
4. Повторное нажатие → `JS_STOP_AND_SEND` (штатная отправка голосового ввода).
5. Если запись не началась — приложение говорит об этом и **не отправляет
   ничего** (`mic.native_verify`, статус «Запись не началась…»).

### 2.2. Одинаковая работа у всех

| Риск | Как снят |
|---|---|
| Разный DPI → разная раскладка и сдвиг текста | **Нативный зум 67 %** (уровень −2.2239 = 2/3) пишется в профиль до запуска, затем **измеряется**: раскладка `размер окна / 0.667` CSS px (620×976 при 100 %, 125 % и 150 % — одинаково) и `innerWidth × dpr = физическая ширина окна`, то есть страница вписана, а не обрезана. Если профиль проигнорирован — зум ставится по CDP и снова измеряется. |
| Стена согласия (ЕС) | Кликер на всех языках + **цель CDP никогда не выбирается на `consent.google.com`/`accounts.google.com`**; профиль постоянный, согласие принимается один раз. |
| Профиль занят / синглтон | Свой `--user-data-dir`; при таймауте — повтор со **свежим** профилем (`browser-profile-retry1`, `-retry2`). |
| Зависание GPU | Повтор с `--disable-gpu --disable-gpu-compositing --disable-software-rasterizer`. |
| Браузер без голосового ввода | Проверка `browser.speech_surface` (`SpeechRecognition`/`getUserMedia`); если нет — автоматический переход к следующему браузеру из списка. |
| Не найден подходящий браузер | Порядок: закреплённый `browser\chrome.exe` → установленный Chrome → Edge → другие Chromium; если нет ничего — резервный встроенный движок с честным статусом. |
| Окно не встроилось | Любая ошибка `SetParent` откатывается: пользователь не остаётся с невидимым или оторванным окном. |
| Страница не стала чатом | Перезапуск браузера целиком (до 2 раз) вместо «висит и ждёт». |

Без `tools\fetch_chrome.bat` приложение само найдёт установленный Google

результатов нет). Поэтому **закреплённый Chrome for Testing — рекомендуемый
путь**: он брендированный, то есть с рабочим речевым сервисом.

## 5. Ограничения (честно)

* **Штатный микрофон требует брендированного Chrome.** В vanilla/ungoogled
  Chromium и в Edge объект `SpeechRecognition` либо отсутствует, либо молчит.
  Поэтому в комплект рекомендуется закреплённый Chrome for Testing
  (`tools/fetch_chrome.bat`); приложение проверяет возможность и само
  переключается на следующий браузер.
* Распознавание — облачное (Google): нужен интернет. Качество и язык зависят от
  сервиса Google, а не от нашего кода.
* Автоматизация по-прежнему зависит от DOM Google: при редизайне сайта
  селекторы кнопки микрофона/отправки нужно обновить (логи подскажут:
  `mic.native_button_missing`).
* Окно браузера — дочернее окно другого процесса: фокус передаётся по клику
  (`browser_focus.py`). Это нормальная практика для встроенного Chromium.

## 6. Сборка EXE (Nuitka)

### 6.1. Подготовка (Windows 10/11 x64)

1. Установить **64-битный Python 3.11+** и **Visual Studio Build Tools**
   (компонент «Средства разработки C++»). При отсутствии MSVC можно собрать
   ключом `--mingw64` (Nuitka сам скачает компилятор), но эталонная сборка
   шла через MSVC.
2. В папке решения:

```bat
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-build.txt
```

`requirements-build.txt` включает `requirements.txt` (PyQt6, PyQt6-WebEngine,
requests, websocket-client, cryptography, fpdf2) и Nuitka с зависимостями
сборки. Других пакетов не нужно: диктовка — штатный PowerShell +
.NET System.Speech (Windows 10/11).

### 6.2. Релизная сборка — ONEFILE (эталонный синтаксис)

**Отдельный файл с этой командой — `BUILD_ONEFILE.txt`** (синтаксис, разбор
каждого ключа, что делать после компиляции, частые ошибки). Синтаксис из
`release_reference/BUILD_COMMAND.txt` сохранён дословно — команда ниже ничем
от него не отличается по флагам (проверяется автотестом).

**Команда дословно из `release_reference/BUILD_COMMAND.txt`** (проверенная
ранее рабочая форма, ничего не удалять):

```bat
python -m nuitka --onefile --windows-console-mode=disable --enable-plugin=pyqt6 --include-package=requests --include-package=websocket --include-package=cryptography --include-package=fpdf --include-data-file=data/DejaVuSans.ttf=data/DejaVuSans.ttf --windows-icon-from-ico=icon.ico --assume-yes-for-downloads --output-dir=build --output-filename=Legalyze.exe main.py
```

Практически: просто выполните **`build_nuitka.bat`** — он выполняет ту же
команду (флаги и порядок сохранены) и добавляет только лицензию шрифта
`FONT-LICENSE.txt` и метаданные версии файла (`1.0.5.0`), затем проверяет,
что `build\Legalyze.exe` появился.

Результат: **`build\Legalyze.exe` — один самодостаточный файл** (Python,
QtWebEngine, шрифты внутри). Окно консоли отключено, иконка и версия в
свойствах файла проставлены. Админ-манифест не добавляется, логика не
меняется.

### 6.3. Отладочная сборка — standalone (по необходимости)

`build_nuitka_standalone.bat` собирает папку `build\main.dist\` (EXE +
DLL/ресурсы рядом). Удобно для отладки и диагностики; для релиза используйте
onefile. При выдаче standalone раздавайте **все** файлы папки
(включая `QtWebEngineProcess.exe`, ресурсы и locales).

### 6.4. Что делать после компиляции

1. **Проверьте EXE** на сборочной машине: запуск без установленного Python,
   окно приложения поднимается, страница ИИ загружается в GUI.
2. **Развертывание** — скопируйте `Legalyze.exe` (onefile) в целевую папку.
   Рядом ничего класть не нужно: `config.json`, `Шаблон.txt`, логи и профиль

## 7. Чек-лист приёмки на Windows 10 и 11

1. Зум 67 %; логотип скрыт; **при запуске сырой браузер не виден ни на
   мгновение** — только шторка приложения.
2. В логе есть `browser.embedded`, `browser.zoom_prefs` и
   `browser.zoom source=…` — окно встроено и зум подтверждён измерением.
3. **Поле ввода ИИ и поле ответа ИИ стоят на своих местах**: чат целиком
   помещается в окно, ничего не смещено вправо и не выходит за границы — ни при
   100 %, ни при 125 %, ни при 150 %. Метрики: `browser.zoom zoom=0.667`,
   `innerWidth` ≈ **680**, `innerWidth × dpr` = физическая ширина окна,
   `overflow` = 0.
3.0. **Жёлтой полосы «вы используете неподдерживаемый флаг…» нет**: в командной
   строке нет `--use-fake-ui-for-media-stream` и
   `--use-fake-device-for-media-stream` (проверено автотестом).
3.1. Проверить на экране с масштабом **125 % и 150 %**: чат выглядит так же, как
   при 100 % (бывшая «широкая надпись ИИ» и сдвиг вправо исключены).
3.2. **Поле ввода промта стоит на месте**: видно целиком, не уехало вниз, не
   перекрыто нижней панелью. В логе `browser.embedded` содержит
   `inset=[-10, -20, 10, 20]` при 100 % (при 125 % — `[-12, -25, 12, 25]`).
   Если нужно подправить — ключи `browser_dx` / `browser_dy` в `config.json`.
3.3. **В панели задач НЕТ ни одной кнопки браузера**: ни встроенного окна, ни
   вспомогательных. В логе есть `win32.taskbar_hidden style=true delete_tab=true`
   и `win32.taskbar_deleted`.
3.4. **Лишних окон браузера нет**: не открываются новые, прошлые не висят,
   в **Alt+Tab** их тоже нет — ни одного. В логе `win32.stray_hidden`

3.5. **Элементы браузера скрыты** (нет лишних панелей/кнопок самого
   Chrome) и `.pdf`/`.txt` выгружаются без Ctrl+R.
3.6. Ни на мгновение не видно «появляющегося браузера с нескрытыми
   элементами»: окно скрывается до встраивания, а шторка — нативная (§0.0.3).
3.7. В логе `browser.embedded` поле `inset` = `[-10, -20, 10, 20]` при 100 %
   (`[-12, -25, 12, 25]` при 125 %, `[-15, -30, 15, 30]` при 150 %).
3.5. **Ни одного чёрного окна консоли** ни при старте, ни при перезапуске.
4. Первый запуск в ЕС/Испании (или с чистым профилем): стена согласия
   закрывается сама, чат появляется; в `browser.target_chosen` никогда нет
   `consent.google.com`.
5. F2 скрыть/показать окно — с любого фокуса и раскладки.

## 8. Если что-то не работает

| Симптом | Что смотреть |
|---|---|
| Поле ввода / поле ответа ИИ стоят не там или съехали вправо | смотрите `browser.zoom`: `zoom=1.0` — зум не применился (норма 0.667), `source=emulation-failed` — измерение не сошлось; приложите поля `logical`, `physical`, `innerWidth`, `dpr` |
| Низ страницы (поле ввода) подрезан | `physical` в `browser.zoom` должен быть клиентской областью окна браузера (v13 берёт именно её) |
| В панели задач видна кнопка браузера | смотрите `win32.taskbar_hidden`: `delete_tab=false` — не создался `ITaskbarList`; кнопку возвращает сам Chrome, поэтому скрытие повторяется раз в 5 с |
| Лишние окна браузера не закрываются | `win32.stray_hidden` пуст, хотя окна есть, — значит они не в дереве наших pid; проверьте `browser.leftover_killed` и журнал `browser-pids.json` |
| Поле ввода промта всё ещё низко/высоко | задайте `browser_dy` в `%APPDATA%\Legalyze\config.json` (например `-30` — выше, `-10` — ниже) и перезапустите: пересборка не нужна |
| Виден «сырой» браузер до загрузки | шторка обязана быть нативным окном (`WA_NativeWindow`) — см. §0.0.3 |
| Окна браузера остаются в Alt+Tab | `win32.stray_hidden` должен содержать их hwnd; пусто — значит они не в дереве наших pid: проверьте, что `refresh_pids` отработал и журнал `browser-pids.json` не пуст |
| Элементы браузера не скрылись, файлы не экспортируются | в логе ищите `AttributeError` в `_on_browser_ready` и `exception` сразу после `browser.ready`: запуск веб-автоматизации оборван |

| Отображение отличается от pre14 | сравните `browser.zoom`: `css` должен быть `658x1091` при окне 439x728, а `zoom` — `0.667`. Если `css` = `679x…` — цель считается от плейсхолдера, а не от окна |
| Мелькает чёрное окно консоли | ни один `Popen` не должен идти без `CREATE_NO_WINDOW` (проверено автотестом) |
| Снова жёлтая полоса про флаг | в логе `browser.launch` видны все аргументы; флагов `use-fake-ui/device-for-media-stream` там быть не должно |
| Микрофон не запускается | `browser.permissions` (права в профиле) и `browser.mic_granted state=…`: `granted` — право есть, `prompt`/`denied` — Chrome не принял права профиля |
| «Не найден Chrome/Edge» | выполните `tools\fetch_chrome.bat` (или укажите `browser_path` в `%APPDATA%\Legalyze\config.json`) |
| `browser.retry` в логе | причина повтора: `devtools-timeout` (профиль/GPU), `window-timeout`, `embed-failed` |
| `browser.speech_surface` без `sr` и `gum` | это сборка без речевого сервиса — приложение само пробует следующий браузер; поставьте закреплённый Chrome |
| `mic.native_button_missing` | изменился DOM сайта — селекторы кнопки микрофона нужно обновить |
| Окно пустое/чёрное | в логе `embed.SetParent` с `actual != expected` — встраивание не удалось, выполнен откат |
| Текст съехал вправо / выходит за границу | смотрите `browser.zoom`: `source=failed` — зум не удалось ни записать в профиль, ни поставить по CDP; проверьте, что профиль доступен для записи, и поставьте закреплённый Chrome (`tools\fetch_chrome.bat`) |
| Широкая раскладка «ИИ» после перезагрузки | сторож зума возвращает масштаб; если повторяется часто — смотрите `browser.zoom_restored` и `browser.zoom` |

| GUI «пропал» при первом запуске | так выглядела шторка «Промт не выбран»: теперь она информационная, а диалог выбора открывается сам |

| На другом разрешении/масштабе браузер уехал в угол или в сторону | смотрите `main.screen_metrics_changed` (`dpr`, `scale`, `inset`) и `browser.embedded` (`inset`): сдвиг обязан быть кратен масштабу — при 150 % `[-15,-60,15,60]` |

| Промелькнули элементы браузера при «Ожидании страницы» | шторка поднимается ДО `ShowWindow` (§0.0.0.1) и повторно на 300…4000 мс; сторож работает с самого старта, а не только после `ready` |

| Браузер не открылся после выбора промта | шторку снимает `upload.attachments_confirmed` (`_on_files_attached`); если выгрузка не удалась — смотрите `upload.failed` |
| **«В Windows не установлен распознаватель речи»** | это симптом «настоящего Chrome нет, работаем на резервном движке». Лечится установкой браузера: в логе ищите `browser.offer candidates=[…]` и `browser.installed`. Пакеты Windows ставить **не нужно** — со штатным браузером запись идёт микрофоном самой страницы (§0.0.0.1) |
| Установка браузера не началась | в логе `browser.install_failed reason=…`: нет интернета/прокси/антивирус. Офлайн-путь — `tools\fetch_chrome.bat`, затем перезапуск |
| Вопрос про установку не задаётся | так и задумано, если Chrome/Edge-подобный брендированный браузер найден или раньше был ответ «Нет» (`browser_install_declined` в `config.json` — удалите ключ, чтобы спросить снова) |
| **Чёрный прямоугольник после сворачивания** | в логе должен быть `browser.revive`. Нет его — смотрите `main.revive_win32` / `main.revive_cdp` / `main.revive_sync` в исключениях; отключить механизм можно ключом `REVIVE_AFTER_SHOW = False` (§0.0.0.2) |
| **Объекты съехали и встали на место через 1-2 с** | лечится в v18.1–v18.3 (§0.0.0-bis.2, §0.0.0-ter, §0.0.0-quater): окно переносится синхронно, раскладка прибивается одним вызовом CDP, а до полной стабилизации стоит GUI прогрузки. Если осталось — пришлите лог: `browser.revive` (`ms`, `settled`, `signature`), `browser.zoom_pinned` / `browser.zoom_restored reason=…`, `browser.revealed stable=…` |
| **Сильно мигает при развороте окна** | лечится в v18.3 (§0.0.0-quater.1): пока стоит GUI прогрузки, окно браузера не трогается вообще — вся работа с окном делается один раз, в финализации. Раньше окно дёргали на каждом шаге, и Chrome поднимал его поверх шторки |
| **GUI прогрузки снимается слишком рано (видно недогруженную страницу)** | **v19** (§0.0.0-quinquies.2): готовность — это `readyState == "complete"` + поле ввода + два одинаковых замера. Смотрите `page.wait` / `page.ready` / `webengine.chat_ready ready=…`. `ready=false` и `blocked=timeout` — страница не дошла до `complete` (причина в `page.surface`: `pending`, `verdict`) |
| **GUI прогрузки снялся, а объекты ещё едут** | **v19** (§0.0.0-quinquies.8): перед снятием ждём `complete` ещё до `REVIVE_REVEAL_GATE_MS`. В логе `browser.reveal_gate ready=…`: `false` — предел, `null` — нет соединения со страницей |
| **Страница тёмная, хотя тема светлая** | **v19** (§0.0.0-quinquies.3): ищите `page.theme_probe` (цвет `body`) и `warn.dark_theme_measured`. Если цвет так и остался тёмным — пришлите лог: видно, применялось ли исправление и сколько раз |
| **`.pdf` и `.txt` не прикрепляются** | **v19** (§0.0.0-quinquies.4): ищите `warn.upload_blocked` — там вердикт поверхности и числа (`files`, `chips`, `composer`, `account`). Вердикт `ai_mode` — сервис отдал режим ИИ в поиске, приложение само откроет рабочую страницу (`page.surface_corrected`) |
| **Приложение упало с «access violation»** | **v19** (§0.0.0-quinquies.1): vtable больше не разыменовывается из Python. Если падение осталось — пришлите `stacks.log` и `summary.json`: в сводке будут все исключения со счётчиками |
| **Один и тот же exe ведёт себя по-разному на двух машинах** | **v19** (§0.0.0-quinquies.5): сравните `env.contract` двух логов построчно (браузер, ключи запуска, зум, язык, тема, размеры) и `browser.prefs_verified` / `browser.prefs_drift` |
| `browser.revealed stable=False` | за 2 с браузер не устоялся: окно или раскладка продолжали меняться. Смотрите поле `signature` в `browser.revive` — какие значения «плавают» |
| Шторка не снимается | не может: последний шаг каденса (2000 мс) и сторож (3500 мс) снимают её в любом случае; в логе ищется `browser.settle_watchdog` |
| В логе много `browser.zoom_restored reason=revive` | раскладка действительно съезжает при показе окна; каденс «оживления» можно удлинить через `REVIVE_STEPS` в блоке настроек |
| После «оживления» съехала раскладка | быть не должно: метрики «дёргаются» только когда они уже равны цели зума (проверка по `innerWidth`). Если всё же изменились — сравните `browser.metrics_nudged` и `browser.zoom` |
| Голос распознаётся не по-русски | проверьте `browser.locale_prefs lang=ru-RU`, `--lang=ru-RU` в `browser.launch` и `page.language_theme locale=…`. Язык можно задать ключом `speech_lang` в `config.json` (§0.0.0.3) |
| Страница тёмная | проверьте `page.language_theme` (`color_scheme=light`) и наличие `WebContentsForceDark` в `browser.launch`. Отключить принудительную светлую тему — `light_theme: false` в `config.json` (§0.0.0.4) |
